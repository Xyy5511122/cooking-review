## 0. 为什么这里没有阈值

`PROTOCOL.md §3` 规定 N2 不允许新增标准。本节点的判定全部是**等值 / 集合相等 / 计数**，
没有形容词，也没有「好不好看」这类需要人来判的条款。若评审方认为某条该有阈值而这里没有，
按 `N2_acceptance/README.md §6` 的纪律记为**规格缺陷**，回 N1 修订并升版本号，
不在验收现场补标准。

## B. 判定规则

| 规则 | 内容 |
|---|---|
| B1 | 实测与期望不符 → 该条记 FAIL；执行方结论若仍写「完工」，即数字与结论矛盾 |
| B2 | 表内数字一律以 `FACTS.md` 为准，README 的叙述不覆盖数字 |
| B3 | 找不到对应数字 → 记「无证据」，不是 PASS |
| B4 | 表 4 三种 bbox 口径（含端点 min/max、半开 XYXY、`[x,y,宽,高]`）不可混用；相差 1px 属口径差异 |

## D. 明确不可判定（归用户，不进 N2 判定）

| 项 | 为什么 |
|---|---|
| 手够不够大、切口好不好看 | 审美判断，模型只看得到数字 |
| 卡通主体 vs 豆包写实落料的风格折中 | 无阈值，只能由用户裁决是否单独开轮 |
| Q/E 手感、节奏、提示文案 | 无真人试玩数据，`FACTS.md` 里没有对应数字 |
| 镜像手是否算「真右手」 | 语义判断；数字只能证明它是逐像素镜像（见 README 主张 C4） |

## E. 数字无法独立复现

`FACTS.md` 的输入文件位于私有 Unity 仓库与工程外暂存目录，公开仓库只有生成脚本与输入 SHA256。
评审方**不能重跑命令**，只能核对命令、哈希与逻辑自洽。这削弱了 `README.md` 的「任何结论都必须能被一段脚本推翻」，
已在 `N2_acceptance/README.md` 主张 C5 单独列出。
